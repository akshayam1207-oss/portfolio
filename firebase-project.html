Objective of the Firebase IoT monitoring system

The goal of this task was to stand up a complete Firebase-backed web app — hosting, a login screen, and a database to hold live sensor data — before wiring up any hardware at all. The problem being solved is giving an IoT device a cloud-hosted, login-protected home: a dashboard reachable from any browser, anywhere, that can display live readings and accept control commands, backed by a database that keeps a history of everything, not just the latest value. I wanted the dashboard itself fully working and deployed first, so Task 5 could focus purely on getting real data flowing into it.

Basic concept of Cloud Computing

Cloud computing means using computing resources — servers, storage, databases, networking — that are owned and run by someone else (here, Google, through Firebase) and rented over the internet, instead of buying and maintaining physical servers. For this project it means the dashboard's files, the login system, and the database all run on Google's infrastructure. I only write code and configuration; Google handles the servers, uptime, scaling and security patching underneath.

IaaS, PaaS, SaaS, and BaaS explained

ModelWhat it gives youExample
IaaS (Infrastructure as a Service)Raw virtual machines, storage and networking — you manage the OS and everything above itGoogle Compute Engine, AWS EC2
PaaS (Platform as a Service)A ready-made platform to deploy your own application code onto, without managing serversGoogle App Engine, Heroku
SaaS (Software as a Service)A complete, ready-to-use application you just log intoGmail, Google Docs
BaaS (Backend as a Service)Ready-made backend building blocks — auth, database, hosting, storage — that your own frontend code calls directlyFirebase (used in this project)
Where this project fits. Firebase is a BaaS. I never provisioned a server or wrote backend API code — Authentication, the Realtime Database and Hosting are backend services I call directly from the dashboard's JavaScript and from the ESP32's firmware.

What a Cloud Platform is, and what a Database is

A cloud platform is a provider's full set of hosted services — compute, storage, databases, authentication, networking — offered together under one account and one console, so an application can be built almost entirely from managed pieces instead of custom infrastructure. Firebase is Google's cloud platform for app backends.

A database is organized, persistent storage for data that can be queried, updated and retrieved reliably over time, instead of being held only in a program's memory (which disappears the moment the device restarts). Databases are broadly either relational / SQL (data in fixed tables with rows and columns, related by keys) or non-relational / NoSQL (more flexible structures such as documents or trees). Firebase's Realtime Database is a NoSQL, JSON-tree-structured database.

Firebase Realtime Database explained

The Firebase Realtime Database stores data as one large JSON tree, rather than tables. Any client — the dashboard's JavaScript or the ESP32's firmware — can read or write to a specific path in that tree (for example /current/temperature), and every other client that has an active listener on that path (or a parent of it) is pushed the updated value within about a second, over a persistent WebSocket connection. That live push is what makes the dashboard update without the browser ever refreshing the page.

Why not a normal SQL database here? A relational database is a better fit for complex relationships and heavy querying. This project needed something simpler: a shared JSON tree that any client can read and write with near-instant sync to every other connected client, with no server-side API code to write — exactly what the Realtime Database is built for.

What a Cloud-Based Dashboard is

A cloud-based dashboard is a web interface, hosted remotely rather than run from a single device, that reads live and historical data from a cloud backend and presents it visually — cards, tables, charts — while also sending commands back to that same backend. Because it's reached over the internet rather than the local network (unlike Task 1's web server), it can be opened from any browser, on any device, anywhere, as long as the person logs in.

Authentication and the purpose of a login system

Authentication is the process of proving who is making a request — in this project, proving that whoever opened the dashboard URL is actually an account I added, by checking an email and password against Firebase Authentication. The purpose of a login system here is straightforward: the dashboard shows live sensor readings and can switch a real 230V bulb, so it should not be reachable or controllable by anyone who simply discovers the Hosting URL.

Difference between Authentication and Authorization

AuthenticationAuthorization
Question answered"Who are you?""What are you allowed to do?"
When it happensAt login — email + password are checkedAfter login — every read/write request is checked against rules
In this projectFirebase Authentication verifying the email/password on the login pageRealtime Database security rules deciding whether a signed-in user can read/write /current, /history, /settings and /control
How they work together. Authentication confirms an identity once, at sign-in. Authorization is enforced on every single database operation after that — a signed-in user is still only ever allowed to do what the security rules ("auth != null" in this project's rules) permit.

System architecture and data-flow

Both clients — the browser dashboard and the ESP32 — talk to the same Firebase project: Authentication to prove identity, the Realtime Database to read/write data, and Hosting to serve the dashboard's files.

Firebase project setup documented

Step 1 — Creating the Firebase project

I started in the Firebase console and created a brand new project, naming it Smart IoT Monitoring. This project became the home for everything else in this task — Hosting, Authentication, and the Realtime Database all live under it.

Step 2 — Registering a web app and getting the Firebase config

Next, I registered a web app inside the project, which gave me a Firebase configuration snippet — apiKey, authDomain, projectId, storageBucket, messagingSenderId and appId. This is the key that lets both the web dashboard and, later, the ESP32 firmware talk to this specific Firebase project.

Step 3 — Setting up the local Firebase CLI

On my machine, I checked my Node.js and npm versions, then installed the Firebase CLI globally with npm install -g firebase-tools. Once installed, I confirmed the version with firebase --version and logged into my Firebase account with firebase login.

Step 4 — Setting up the project folder and initializing Hosting

I confirmed the project existed from the CLI's point of view with firebase projects:list, then created a dedicated folder for the hosting files — Smart-IoT-Monitoring inside my Desktop — and ran firebase init hosting from inside it. I linked it to the existing Smart IoT Monitoring project, set public as the hosting directory, and declined the single-page-app rewrite and GitHub Actions options since I didn't need them.

Step 5 — Deploying to Firebase Hosting

After testing the hosting files locally, I deployed everything with firebase deploy. The CLI uploaded the files, finalized a new hosting version, and released it — giving me a live Hosting URL for the dashboard.

Firebase Authentication configuration documented

For the login screen, I enabled the Email/Password sign-in provider under Authentication → Sign-in method, then added the specific user accounts allowed to access the dashboard under Authentication → Users. No public sign-up form exists anywhere in the app — accounts are only ever added from the Firebase console, which is deliberate: the dashboard controls a real appliance, so I wanted account creation to stay fully under my control rather than self-service.

function renderHistoryTable(rows) {
  const tbody = document.getElementById('historyBody');
  tbody.innerHTML = rows.slice().reverse().map((r) => `

      <td>${r.temperature} °C</td>
      <td>${r.humidity} %</td>
      <td>${r.ldr}</td>
      <td>${r.bulbStatus ? 'ON' : 'OFF'}</td>
      <td>${(r.mode || '').toUpperCase()}</td>

function renderHistoryChart(rows) {
  const labels = rows.map((r) => new Date(r.timestamp).toLocaleTimeString());
  const data = {

DHT11 temperature and humidity monitoring

In Arduino IDE, I wrote the ESP32 sketch and set up the credentials it needed at the top: the Wi-Fi SSID and password, the Firebase Web API key, the Realtime Database URL, and the email/password of the Firebase Authentication user the board signs in as before it's allowed to read or write any data. The DHT11 is read once per cycle alongside the LDR.

#include <DHT.h>
#define DHTPIN  4
#define DHTTYPE DHT11
DHT dht(DHTPIN, DHTTYPE);

dht.begin();                            // in setup()

float temperature = dht.readTemperature();   // °C
float humidity    = dht.readHumidity();      // %
if (isnan(temperature) || isnan(humidity)) {
  Serial.println("DHT11 read failed, skipping this cycle");
  return;
}

LDR-based light level monitoring

I mapped out the pins for the LDR, relay, and DHT11, created the Firebase data/auth/config objects, and used the Serial Monitor to confirm the board was reading real values and preparing each payload correctly — LDR reading, temperature, humidity, current mode, and bulb state — before trusting it to actually send anything.

#define LDR_PIN 34
int ldrValue = analogRead(LDR_PIN);     // 0–4095 on the ESP32's 12-bit ADC

Manual bulb control

In Manual mode, the Bulb ON and Bulb OFF buttons on the dashboard write directly to /settings/mode ("manual") and /control/bulbCommand (true/false). The ESP32 keeps a live Firebase stream open on /control, so the moment the dashboard writes a new command it is pushed to the board and applied to the relay — no polling delay.

if (Firebase.readStream(fbStream)) {
  if (fbStream.streamPath() == "/control" && fbStream.dataPath() == "/bulbCommand") {
    bulbState = fbStream.boolData();     // dashboard button pressed
  }
}

Automatic bulb control using the LDR

In Automatic mode, the firmware instead compares the live reading from the LDR module against a threshold value set on the dashboard. Covering the LDR blocks light from reaching it, so its reading drops below the threshold — the ESP32 reads this as "it's dark now" and automatically switches the bulb ON. Uncovering it lets light back in, the reading rises back above the threshold, and the ESP32 automatically switches the bulb OFF again.

if (mode == "auto") {
  bulbState = (ldrValue < ldrThreshold);   // dark -> ON, bright -> OFF
}
digitalWrite(RELAY_PIN, bulbState ? HIGH : LOW);

LDR threshold / calibration method

To pick a usable threshold, I watched the raw LDR reading on the Serial Monitor under normal room lighting versus with the sensor fully covered, and used the midpoint between the two as the starting threshold — 800, the value shown on the dashboard in the screenshot above. Because settings/ldrThreshold is a normal database field rather than a constant baked into the firmware, it can be recalibrated for a different room or lighting condition directly from the dashboard, without re-flashing the ESP32.

Historical data logging in Firebase

Every reading cycle (roughly every 2 seconds), in addition to overwriting the single /current snapshot, the firmware also pushes a new entry under /history — Firebase's push() generates a unique, chronologically-ordered key for each entry automatically, so nothing is ever overwritten and the full sequence of readings is preserved for the table, the chart and the CSV export.

FirebaseJson entry;
entry.set("temperature", temperature);
entry.set("humidity", humidity);
entry.set("ldr", ldrValue);
entry.set("bulbStatus", bulbState);
entry.set("mode", mode);
entry.set("timestamp/.sv", "timestamp");   // Firebase server-side timestamp
Firebase.pushJSON(fbData, "/history", entry);

Problems encountered and solutions implemented

Limitations of the current prototype

  • A single DHT11 gives only room-level temperature and humidity, with no fine-grained calibration against a reference instrument.
  • The LDR threshold is a simple fixed cutoff with no hysteresis, so Automatic mode can flicker when the light level sits right at the threshold.
  • If the ESP32 loses Wi-Fi, readings during that gap are lost rather than buffered locally and sent once reconnected.
  • Only one relay channel is wired, so the system can control a single appliance rather than multiple independent loads.
  • /history grows indefinitely in the database with no automatic pruning or archiving policy.

Possible future improvements

  • Add hysteresis around the LDR threshold (for example, two separate on/off thresholds) to stop flickering in Automatic mode.
  • Buffer readings locally on the ESP32 during a Wi-Fi outage and resend them once the connection is restored.
  • Add Firebase Cloud Messaging push notifications for threshold crossings or the device going offline.
  • Support multiple relay channels for independently controlling more than one appliance.
  • Add a scheduled Cloud Function to archive or prune old /history entries automatically.
  • Move credentials out of the firmware source into a provisioning step, rather than hard-coded constants.

Final learning reflection

What I learned

This task was where the project stopped being just "a device with sensors" and became a real product: live temperature and humidity on a dashboard I could open from any browser, a bulb I could switch manually or let respond automatically to the LDR, and a logged history I could chart or export as CSV. Structuring the database into current/history/settings/control before writing a single line of firmware meant the ESP32 code always knew exactly where to read and write, and logging every reading to history instead of only overwriting "current" is what made the chart and CSV export possible later — a decision that had to be made on day one, not added afterward.

Result: the ESP32 and its sensors fully integrated with the Firebase dashboard from Task 4 — live readings, working bulb control in both Manual mode and an Automatic mode driven by the LDR's ambient-light threshold, and a logged, chartable, CSV-exportable history, all behind the login screen.

Key Learnings

What Building the Firebase Dashboard Taught Me

Splitting this into two tasks — build the platform first, then connect the hardware — turned out to be the most useful decision of the whole project.

  • Getting Firebase Hosting, Authentication, and the Realtime Database working and deployed before touching any hardware meant Task 5 was purely about the ESP32 side, with nothing else to debug at the same time.
  • The Firebase CLI workflow — firebase login, firebase init hosting, firebase deploy — is a genuinely quick way to go from a blank project folder to a live, public URL.
  • A login screen isn't just for looks — putting the dashboard behind Firebase Authentication meant the sensor data and bulb control were only reachable by accounts I'd explicitly added.
  • Structuring the Realtime Database ahead of time (current / history / sensors / settings) made the ESP32 firmware much simpler to write, since it always knew exactly where to write and read each value.
  • The same API key, database URL, and Authentication credentials used for the web app are what let the ESP32 write into the exact same project — the dashboard and the firmware are really just two different clients of one shared backend.
  • Logging every reading to a history node, not just overwriting the "current" value, is what makes charts, trends, and CSV export possible later — that decision has to be made in the firmware from day one.
  • A single sensor can drive two very different behaviours depending on the mode it's read in — the same LDR value is just a number on the dashboard in Manual mode, but becomes an automatic on/off trigger the moment Automatic mode compares it against a threshold.
Reflection

This project made the gap between "a device with sensors" and "a real product" much clearer to me. Task 4 was almost entirely about infrastructure — hosting, login, and a database schema — before a single sensor reading existed. Task 5 was where it actually became a product: real temperature and humidity on a live dashboard, a bulb I could switch from a browser in Manual mode or let respond automatically to the LDR sensor in Automatic mode, and a history I could look back through or export. Seeing the same Firebase project serve both the web app and the ESP32 firmware helped me understand backends as something shared across multiple kinds of clients, not just "a website's database." That's a pattern I expect to reuse in almost every connected project from here on.
